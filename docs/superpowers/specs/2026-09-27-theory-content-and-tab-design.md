# Theory content pipeline + Theory tab

Status: approved for implementation planning.

## Why

Students hit Mission/practice questions with no prior explanation of the
underlying concept. The redesign brainstorm (see the visual-redesign work
earlier this session) surfaced a second, content-shaped gap: there is
nowhere in the app that *teaches* a concept before the student is asked to
apply it. This spec covers building that teaching layer — a "Theory" tab —
and the content pipeline changes needed to author its lessons.

`docs/PLAN.md` §3 describes a 4-tab nav of Today/Skill Map/Tests/Me as the
target design; that section is superseded here. The new target is
**Today · Theory · Mission · Tests · Me** (5 tabs), with Theory tab-ordered
before Mission per explicit direction. `Skill Map` as a name and screen is
retired: its chapter-list-with-mastery-and-concepts role becomes the
Mission tab's chapter list (renamed, not rebuilt), and Theory gets its own,
simpler chapter list.

## Scope

Pilot: **Surface Areas & Volumes** only (CBSE Class 9 Maths), one lesson
per concept (7 lessons — the chapter has 7 concepts). Hand-authored YAML,
not generated by the AI pipeline — matches the "hand-author a pilot first"
decision. Automating lesson generation is explicitly out of scope here.

## Content schema

New sibling file to the existing mission YAML:
`content/questions/cbse/9/maths/surface_area_volume_theory.yaml`

```yaml
lessons:
  - id: t_c9_sav_cuboid_cube
    concept_id: c9.sav.cuboid_cube
    title: "Cuboids & Cubes"
    body: >
      A cuboid is a box shape: two matching ends, four flat sides, every
      corner square. A cube is just a cuboid where all three sides are
      equal.
    hook_kind: historical   # or real_world
    hook: >
      Cereal boxes, shipping crates, even the Great Pyramid's casing
      stones were cut to a target surface area to save material. Same
      shape, 4,500 years apart.
    try_it: >
      A shoebox is 30 cm long, 20 cm wide, 15 cm tall. Roughly how much
      cardboard covers it?
    sort_order: 1
```

Field rules (validated by a new pipeline type):
- `id`: globally unique, `t_` prefix (mirrors `q_` for questions).
- `concept_id`: must exist in `content/syllabus/cbse/9/maths.yaml`.
- `title`: short, no period.
- `body`: the one-idea explanation. Plain language; any technical term
  used gets defined in the same sentence or the next. Length-capped (~400
  chars) to force brevity — this is a lesson, not a chapter.
- `hook_kind` + `hook`: `historical` (a real historical/period detail) or
  `real_world` (an everyday application). Required — every lesson grounds
  the idea in something concrete, per the "students learn faster from
  application" instruction. Length-capped similarly to `body`.
- `try_it`: optional, ungraded prompt. No answer stored — it's a nudge to
  think, not a question; Mission is where real practice happens.
- `sort_order`: display order within the chapter (mirrors `concepts`).
- `$...$` math delimiters are allowed and validated the same way question
  text is (`check_latex`), since `MathText` already renders them.

### Pipeline module

`content/pipeline/types/lesson.py` (new, alongside `mcq.py` etc.):
- Not registered in the question-type `REGISTRY` — lessons aren't
  questions and don't go through `validate_bank`/`generate.py`. It's a
  standalone `validate_lesson(lesson: dict, ctx: Context) -> None`
  function reusing `Context`/`check_latex` from `base.py`.
- `content/pipeline/validate.py` gains a call to also walk
  `*_theory.yaml` files and run this validator, so `make pipeline-validate`
  catches lesson content the same way it catches question content.

### Seeding

`content/pipeline/seed_theory.py` (new), structurally identical to
`seed_mission.py`:
- Reads the theory YAML + `cbse/9/maths.yaml` syllabus.
- Writes `backend/supabase/seed/005_surface_area_volume_theory.sql`,
  inserting into the new `lessons` table (chapter/concepts already exist
  from `004_surface_area_volume_mission.sql`, so this seed only adds
  lesson rows).
- Run manually (`python -m content.pipeline.seed_theory`), like
  `seed_mission.py` — not part of the automated `generate.py` flow.

## Database schema

New migration `backend/supabase/migrations/20260930000000_theory_lessons.sql`:

```sql
begin;

create table lessons (
  id         text primary key,
  concept_id text not null references concepts(id),
  title      text not null,
  body       text not null,
  hook_kind  text not null check (hook_kind in ('historical', 'real_world')),
  hook       text not null,
  try_it     text,
  sort_order smallint not null default 0
);
create index lessons_concept_idx on lessons(concept_id);

create table theory_progress (
  user_id   uuid not null references profiles(id) on delete cascade,
  lesson_id text not null references lessons(id),
  read_at   timestamptz not null default now(),
  primary key (user_id, lesson_id)
);

alter table lessons enable row level security;
alter table theory_progress enable row level security;

create policy read_lessons on lessons for select using (true);
create policy own_theory_progress on theory_progress
  for all using (user_id = auth.uid()) with check (user_id = auth.uid());

commit;
```

This exactly mirrors the existing `questions`/`level_progress` pattern:
content table is world-readable to signed-in users, progress table is
own-rows-only. Theory progress is a **separate signal** from
`concept_mastery` — marking a lesson read does not touch mastery. The two
systems stay decoupled; Mission practice remains the only mastery driver.

## Flutter data layer

- `Lesson` model in `data/models.dart`: `id`, `conceptId`, `title`, `body`,
  `hookKind` (enum `HookKind { historical, realWorld }`), `hook`,
  `tryIt` (nullable), `sortOrder`.
- `ContentRepository.fetchAll()` gains a `lessons` query (mirrors the
  existing `questions` query shape), folded into `ContentSnapshot` as
  `List<Lesson> lessons`.
- `Content` gains `lessonsForChapter(chapterId)` and
  `lessonForConcept(conceptId)` helpers, alongside the existing
  `forChapter`/`forConcept`.
- `TheoryProgressRepository` (new, mirrors `LevelProgressRepository`):
  `fetchAll()` returns `Set<String>` of read lesson ids for the signed-in
  user; `markRead(lessonId)` upserts into `theory_progress`.
- `theoryProgressProvider` (new, mirrors `levelProgressProvider` /
  `TheoryProgressState` mirrors `LevelProgressState`), exposing
  `isRead(lessonId)` and `readCountForChapter(chapterId)`.

## Flutter UI

### Bottom nav (`app_shell.dart`)

Tabs become: **Today · Theory · Mission · Tests · Me** (5 tabs, Theory
before Mission). `SkillMapScreen` is renamed `MissionListScreen` (file
moves `features/skill_map/` → `features/mission/mission_list_screen.dart`,
or stays in place renamed — implementer's call) and keeps its exact
current behavior unchanged: subject switcher, chapter cards with mastery
ring, expandable concept list with mastery chips + per-concept Practice
button, "Start Mission" CTA.

### `TheoryScreen` (new, `features/theory/theory_screen.dart`)

Same shell as the Mission list (reuses `_SubjectSwitcher`), but each
chapter card is simpler:
- A ring showing `lessons read / total` (reuse `MasteryRing`'s visual
  language, driven by `theoryProgressProvider`, not `concept_mastery`).
- Chapter name + "N lessons".
- Tapping the card pushes a lesson list (or expands inline — implementer's
  call during planning) showing each lesson's title with a read/unread
  indicator.
- Tapping a lesson pushes `LessonScreen`.

### `LessonScreen` (new, `features/theory/lesson_screen.dart`)

- Title (Fraunces display).
- Body text (`MathText`, plain paragraph).
- A "hook" card styled distinctly (per the approved mockup's story-panel
  treatment: tinted background, dashed/solid accent border, small eyebrow
  label reading "Where this shows up" for real_world or "A bit of
  history" for historical).
- If `try_it` is present, a lightweight prompt card (no input, no
  grading — just text, inviting the student to think before moving on).
- "Mark as read" `ChunkyButton` at the bottom — calls
  `theoryProgressProvider.markRead(lesson.id)`, then pops back. Re-opening
  an already-read lesson shows the button as already toggled/disabled
  (implementer's call on exact treatment) rather than re-marking.

### Chapter-level progress visibility

Per earlier direction ("show progress for each chapter in the mission and
theory tab"): the Mission tab's chapter card already shows mastery-based
progress (unchanged). The Theory tab's chapter card shows lesson-read
progress. Cross-showing (e.g. a small Theory-read badge on the Mission
tab's card) is **not** in this pilot's scope — each tab shows its own
progress type only, to keep the first cut simple.

## Testing

- Pipeline: `content/pipeline/tests/test_lesson.py` (new) — mirrors
  `test_questions.py`'s shape, covers the validator's required-field and
  length-cap checks.
- Flutter: `test/features/theory/theory_screen_test.dart` and
  `test/features/theory/lesson_screen_test.dart` (new) — mirror the
  existing `skill_map_screen_test.dart`/`mission_screen_test.dart`
  patterns (`ProviderScope` + `MaterialApp(theme: AppTheme.light, ...)`,
  per the fix made earlier this session).
- `content_repository_test.dart` gains a case for parsing a `lessons` row.

## Out of scope for this pilot

- Generating lesson content via the AI pipeline (`generate.py`-style).
  Hand-authored only, for now.
- Gating Mission behind Theory completion (explicitly decided: independent
  tracks, Theory just recommended first).
- Any lesson content beyond Surface Areas & Volumes.
- Cross-tab progress badges (Theory-read indicator on the Mission tab or
  vice versa).
